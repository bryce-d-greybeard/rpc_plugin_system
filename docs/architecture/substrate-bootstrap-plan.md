# Substrate bootstrap hardening plan

## Problem

The current substrate bootstrap path in `rpc_plugin_system` is better than the old env-private-key handoff in `agent-memory`, but it still couples too much through a narrow one-time token file and a post-launch RPC auth call.

Current properties:
- per-plugin runtime dir
- one-time bootstrap token generated by substrate manager
- token written to a private auth file
- plugin loads token at startup
- manager later authenticates over RPC with `Auth(Token)`
- peer credentials on the Unix socket are checked

This is already a real bootstrap, but the boundary is still too thin:
- bootstrap authorization still leans on a bearer token in the transitional auth step
- session derivation now exists, but encrypted steady-state RPC and immediate refresh policy still need to be fully finished
- transport was filesystem-token-file based rather than explicit bootstrap endpoint based, though the live POSIX path now uses explicit FIFO endpoints
- Windows transport parity is not part of the contract
- bootstrap/auth/session concerns are not separated clearly enough for future capability scoping

## Goal

Narrow and harden the substrate-owned bootstrap/session boundary by moving toward:
- per-plugin, per-launch bootstrap transport
- one-time bootstrap token bound to launch/session identity
- substrate-owned ephemeral DH session establishment
- generation-based refresh/rekey
- shared protocol with POSIX and Windows transport adapters

This belongs in substrate core, not in keyring and not in optional plugins.

## Non-goals

Do not mix in:
- keyring manager policy
- application-level authorization redesign
- secret-store implementation
- decorative IPC frameworks
- substrate-wide rewrite in one patch

## Current baseline to preserve

Any transition must preserve these existing guarantees unless intentionally replaced:
- runtime dir must be private and non-symlinked
- plugin executable must be absolute, regular, executable, and not group/world writable
- socket peer credentials must still be checked where supported
- bootstrap state must remain per-plugin and per-launch
- failed launch must clean up socket/auth artifacts

## Recommended patch sequence

### Patch 1: define bootstrap/session contract
Add a substrate architecture contract document and protocol types.

Files:
- `docs/architecture/substrate-bootstrap-plan.md`
- `internal/bootstrap/protocol.go`

Add explicit types for:
- bootstrap version
- plugin id
- launch/session id
- one-time token
- expiry
- substrate ephemeral public key
- plugin ephemeral public key
- rekey generation metadata

This patch is documentation and type scaffolding only.

### Patch 2: add bootstrap transport seam
Add a small transport interface for bootstrap only.

Files:
- `internal/bootstrap/transport.go`
- `internal/bootstrap/transport_posix.go`
- `internal/bootstrap/transport_windows.go`

Transport responsibilities only:
- create endpoint
- expose endpoint locator
- connect/wait
- send bootstrap record
- receive bootstrap response
- close
- cleanup

No auth policy in the transport layer.

### Patch 3: add bootstrap session manager
Files:
- `internal/bootstrap/session.go`

Responsibilities:
- mint one-time token
- assign launch/session id
- enforce expiry
- reject replay
- track consumed bootstrap state

Keep this per plugin and per launch.

### Patch 4: add ephemeral DH and derivation
Files:
- `internal/bootstrap/dh.go`
- `internal/bootstrap/kdf.go`

Responsibilities:
- substrate ephemeral keypair generation
- plugin ephemeral key parsing/validation
- shared secret derivation
- root session key derivation bound to:
  - shared secret
  - one-time token
  - plugin id
  - launch/session id
  - bootstrap transcript/version

Keep the crypto profile explicit and small.

### Patch 5: wire bootstrap endpoint into launch path
Replace direct auth-file token loading as the only bootstrap mechanism.

Current path:
- substrate writes token file
- plugin reads token from file at startup
- manager calls RPC `Auth(Token)`

Target transitional path:
- substrate creates bootstrap endpoint
- substrate passes only endpoint locator plus minimal launch metadata
- substrate sends bootstrap record through endpoint
- plugin responds with token echo plus ephemeral public key
- substrate derives session state
- RPC auth call either becomes a compatibility step or is removed in the next patch

Do this behind a transitional mode flag if needed.

### Patch 6: introduce session state and rekey scaffolding
Files:
- `internal/bootstrap/session_keys.go`
- `internal/bootstrap/rekey.go`

Track:
- root session secret
- current key generation
- send/recv keys
- refresh counters or deadlines

Start with simple generation-based rekey.

Current direction after the live DH cutover:
- derive a real bootstrap shared secret during startup
- immediately refresh key material before steady-state RPC trust is granted
- treat the bootstrap token as bootstrap-only, not as the lasting trust root
- move toward distinct keys for encrypted RPC communication rather than a single placeholder session blob

### Patch 7: collapse legacy token-only auth path
Once bootstrap session establishment and immediate post-bootstrap refresh are real and tested, remove or sharply reduce the old token-only `Auth(Token)` role so the one-time token is bootstrap authorization only, not the lasting session trust mechanism.

## Threat model for first pass

This first pass should aim to improve:
- replay resistance between plugin launches
- ambient credential spread
- confused-deputy plugin startup issues
- per-plugin blast radius
- long-lived session key stagnation

This first pass should not pretend to solve:
- root/admin compromise
- full local same-user process compromise
- binary attestation
- global plugin authorization policy

## Open decisions still required

Before code lands beyond scaffolding, decide:
1. exact crypto profile (`crypto/ecdh` curve choice, KDF, AEAD)
2. whether persistent plugin identity is required or deferred
3. exact rekey trigger policy
4. exact startup failure and replay persistence semantics
5. whether Unix peer credential checks remain mandatory even after DH bootstrap

## Recommendation

Do the simple thing:
- preserve the existing one-time-token substrate baseline only for bootstrap authorization
- add a real bootstrap transport seam
- bind one-time tokens into a substrate-owned DH session bootstrap
- immediately refresh derived key material before steady-state trust
- use refreshed keys as the basis for encrypted RPC communication
- keep the patch stack narrow and reviewable
