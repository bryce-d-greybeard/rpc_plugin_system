# v1.0 checklist

This document is the blunt checklist for when `rpc_plugin_system` may honestly be called `v1.0.0`.

The rule is simple:
- do not start the memory-system implementation until this checklist is satisfied well enough to call the plugin substrate `v1.0.0`

## What v1.0 means here

`v1.0.0` does not mean the project is finished forever.

It means:
- the local standalone plugin substrate is real
- the core contract is stable enough to build on
- failure and restart behavior are credible
- plugin authoring is clear enough for another engineer to use
- operator-facing behavior is documented well enough to trust

## v1.0 categories

The v1.0 bar breaks into six categories:
1. contract stability
2. plugin authoring usability
3. local hardening proof
4. multi-plugin kernel capability
5. compatibility and packaging discipline
6. release discipline

## 1. Contract stability

These must be true:
- API, ABI, compatibility, and standard docs match actual implementation
- required lifecycle semantics are explicit and stable
- required logging semantics are explicit and stable
- required startup environment is explicit and stable
- required wire namespace and method set are explicit and stable
- breaking changes require an intentional version bump

Current status:
- mostly done
- docs are now much closer to reality
- frozen `TestPlugin.*` compatibility is documented

Still needed before v1:
- one explicit v1 contract pass after the remaining feature work lands
- eliminate any lingering v0-era wording that implies uncertainty

## 2. Plugin authoring usability

These must be true:
- `sdk/go/plugin` is clearly the public authoring entrypoint
- a new plugin author can build a minimal plugin without reading internal packages
- there is at least one minimal skeleton example
- startup/auth incompatibility failures are understandable
- public README/tutorial is enough to get a plugin running

Current status:
- partly done and improving
- SDK entrypoint exists and works
- stable minimal template path now exists in `sdk/go/plugin/template.go`
- README/tutorial exists and is being tightened around the public authoring path

Still needed before v1:
- do one final public authoring coherence pass across README, template, and example plugin
- review public naming/messages for author-facing clarity
- verify the authoring path feels stable enough to freeze

## 3. Local hardening proof

These must be true:
- restart behavior is stable under churn
- timeout poisoning is proven under repetition
- transport-break recovery is proven under repetition
- monitor-loop recovery is proven under repetition
- runtime artifacts remain clean under churn
- stale generations are never trusted after failure
- operator-visible state remains coherent during mixed failures

Current status:
- partly done and now credible
- restart storm coverage exists
- timeout storm coverage exists
- transport-break storm coverage exists
- repeated monitor recovery coverage exists

Still needed before v1:
- stronger artifact cleanliness assertions under churn
- one mixed-failure stress run that exercises several failure modes in sequence
- optional peer credential hardening decision: either ship it or explicitly defer it from v1

## 4. Multi-plugin kernel capability

These must be true:
- the kernel can supervise more than one plugin intentionally, not accidentally
- each plugin has isolated runtime artifacts/state
- each plugin has isolated visibility in status and logs
- restart/control operations can target one plugin cleanly
- operator state remains understandable with more than one plugin present

Current status:
- mostly done now
- multi-plugin host/runtime/control work is real
- direct routing by plugin id has an explicit route-target primitive and a small routed-call layer
- route inspection is now explicit through host state, admin RPC, and CLI
- routed `Heartbeat`, `Echo`, and restart are test-backed through the direct-routing layer
- first routing-failure isolation proof now exists: one bad routed target can fail while another healthy target remains routable

This remains one of the biggest remaining structural gaps between the current substrate and an honest `v1.0.0`, but it is close to a freeze-worthy state if the current direct-routing surface is accepted as sufficient for v1.

## 5. Compatibility and packaging discipline

These must be true:
- compatibility expectations are documented clearly
- release-safe public docs/examples are in place
- public repo surface is cleaned of unrelated internal architecture material
- build/test/package flows are straightforward
- branch promotion discipline is clear from `dev` to `testing` to `main`

Current status:
- partly done
- docs exist
- repo surface is cleaner now
- branch model is already chosen

Still needed before v1:
- explicit compatibility matrix or compatibility policy section
- explicit release/promotion checklist
- packaging/install guidance solid enough for another engineer

## 6. Release discipline

These must be true:
- there is a concrete definition of what qualifies for `v1.0.0`
- the repo is coherent on `dev`
- promotion to `testing` is deliberate and tested
- promotion to `main` is deliberate and tested
- v1 docs describe the substrate without hand-wavy caveats

Current status:
- partly done
- the roadmap direction is clear
- the repo is closer to coherent than before

Still needed before v1:
- explicit promotion checklist
- explicit test matrix used before branch promotion
- final v1 readiness pass

## Blunt current assessment

### Already real
- core kernel lifecycle model
- one-time bootstrap token auth
- restart and generation semantics
- shared logging subsystem
- operator log tooling
- substantial failure/stress evidence
- public Go SDK entrypoint

### Not yet honest to call v1
- multi-plugin kernel support is not there yet
- authoring UX still needs a minimal polished skeleton path
- packaging/release discipline is still more implied than nailed down
- a few hardening/repo-discipline items still need to be finished cleanly

## Recommended order from here

1. finish plugin authoring baseline
   - minimal skeleton example
   - tighten README/tutorial
   - improve author-facing error clarity

2. finish local hardening proof
   - mixed-failure stress run
   - artifact cleanliness checks
   - decide on peercred for v1 vs post-v1

3. build multi-plugin kernel support
   - isolated per-plugin runtime dirs
   - per-plugin state visibility
   - targeted restart/control operations
   - clear CLI output for multiple plugins
   - direct routing by plugin id
   - visible capability map
   - direct-routing docs and route inspection surface

4. finish compatibility and packaging discipline
   - compatibility policy/matrix
   - packaging/install guidance
   - release checklist

5. promote through branches honestly
   - `dev` -> `testing`
   - `testing` -> `main`
   - tag `v1.0.0` only when the checklist is truly satisfied

## Decision rule

If the question is "can we build memory on top of this yet?"

The answer should remain **no** until the project can honestly satisfy the sections above, especially:
- plugin authoring usability
- multi-plugin kernel capability
- compatibility/packaging discipline
- release discipline
